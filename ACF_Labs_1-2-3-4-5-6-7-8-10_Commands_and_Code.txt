LAB 1 - NETWORK SCANNING AND RECONNAISSANCE USING NMAP
============================================================

Purpose:
Find active hosts, open ports and service/version information on the assigned lab target.

1. Update package list and install Nmap:
   sudo apt update
   sudo apt install nmap -y

2. Show your machine's IP addresses and interfaces:
   ip addr

3. Test connectivity to the instructor-assigned target:
   ping -c 4 192.168.56.101

4. Discover active hosts on the assigned lab subnet:
   nmap -sn 192.168.56.0/24

5. Perform a basic scan of the assigned target:
   nmap 192.168.56.101

6. Detect service versions:
   nmap -sV 192.168.56.101

7. Optional OS detection (lab target only):
   sudo nmap -O 192.168.56.101

Replace 192.168.56.101 and 192.168.56.0/24 with the actual lab values.

What to record:
- Active target IP
- Open/closed/filtered ports
- Service names and versions
- Suggested remediation for unnecessary/outdated services

LAB 2 - NETWORK PACKET CAPTURE AND ANALYSIS USING WIRESHARK
============================================================

Purpose:
Capture authorized lab traffic and inspect protocols and packet headers.

1. Install Wireshark:
   sudo apt update
   sudo apt install wireshark -y

2. Start Wireshark:
   wireshark

3. In Wireshark:
   - Select the interface carrying lab traffic (for example eth0 or ens33).
   - Click Start.
   - Generate harmless lab traffic from a terminal.
   - Stop the capture after a short period.

4. Generate ICMP traffic:
   ping -c 4 192.168.56.101

5. Generate DNS traffic:
   nslookup example.com

6. Wireshark DISPLAY FILTERS (enter these in the filter bar):
   icmp
   dns
   tcp
   udp
   ip.addr == 192.168.56.101

Note: These are Wireshark display filters, NOT Linux terminal commands.

7. Save the capture:
   File -> Save As -> lab2_capture.pcapng

What to inspect/record:
- Source and destination IP addresses
- Protocol (ICMP, DNS, TCP, UDP)
- Source/destination ports where applicable
- ICMP type/code, DNS query/response, TCP flags
- Do not capture or disclose passwords or confidential traffic.

LAB 3 - VULNERABILITY ASSESSMENT OF AN INTENTIONALLY
         VULNERABLE SYSTEM
============================================================

Purpose:
Perform a safe vulnerability assessment of the instructor-provided vulnerable VM.

Tools:
Greenbone/OpenVAS (or instructor-approved scanner), Kali/Ubuntu, isolated target VM.

1. Check target reachability:
   ping -c 4 <LAB-TARGET-IP>

2. Optional service/version check:
   nmap -sV <LAB-TARGET-IP>

3. Install Greenbone/OpenVAS if your lab image/instructor requires local installation:
   sudo apt update
   sudo apt install gvm -y

4. On Kali installations that use the GVM setup utility, initialize it:
   sudo gvm-setup

5. Check setup/status (availability varies by distribution/version):
   sudo gvm-check-setup

6. Start the service if supported by your installation:
   sudo gvm-start

7. Open the Greenbone web interface shown by the setup/start output.
   - Create a Target using ONLY <LAB-TARGET-IP>.
   - Create a Task for that target.
   - Select the standard/safe assessment profile recommended by faculty.
   - Start the scan and wait for completion.
   - Open the report and record findings and severity.

Important:
Greenbone package names and setup commands can differ by Kali/Ubuntu release.
If Greenbone is already installed in the provided VM, use its web console instead
of reinstalling it. Do not enable destructive exploitation modules.

What to record:
- Finding name and CVE (if listed)
- Severity/risk
- Affected port/service
- Evidence from report
- Recommended remediation

LAB 4 - SAFE MALWARE / SIMULATED MALICIOUS PROGRAM ANALYSIS
============================================================

Purpose:
Observe a harmless file-rename simulation, calculate a hash and document behavior.

Files supplied for this lab:
1. malware_sim.py
2. launcher.py

CONTENT OF malware_sim.py:
------------------------------------------------------------
import os

# Make a dummy file
open("test.txt", "w").write("demo")

# Rename it (fake malware action)
os.rename("test.txt", "test.locked")
print("File renamed to test.locked")

# Restore it
os.rename("test.locked", "test.txt")
print("File restored to test.txt")
------------------------------------------------------------

CONTENT OF launcher.py:
------------------------------------------------------------
import os

print("Starting malware simulation...")
os.system("python malware_sim.py")
print("Simulation finished.")
------------------------------------------------------------

A. Prepare the isolated lab folder:
   mkdir -p ~/acf_lab4
   cd ~/acf_lab4

B. Put BOTH supplied files (malware_sim.py and launcher.py) in this SAME folder.
   If they are in Downloads, copy them (adjust the source path if needed):
   cp ~/Downloads/malware_sim.py .
   cp ~/Downloads/launcher.py .

C. Confirm both files are present:
   ls -l

D. Check Python:
   python3 --version

E. Calculate SHA-256 before running:
   sha256sum malware_sim.py
   sha256sum launcher.py

F. Identify file type:
   file malware_sim.py
   file launcher.py

G. Run the launcher (from the folder containing both files):
   python3 launcher.py

Expected output:
   Starting malware simulation...
   File renamed to test.locked
   File restored to test.txt
   Simulation finished.

H. Run the simulation directly, if required:
   python3 malware_sim.py

I. Check the created/restored dummy file:
   ls -l test.txt
   cat test.txt

J. Calculate hash of the script again if you need to verify it was not changed:
   sha256sum malware_sim.py

K. Clean up the harmless test file after the practical:
   rm -f test.txt test.locked

IMPORTANT NOTES:
- launcher.py calls "python malware_sim.py". On some Linux systems, the command
  "python" may not be installed even though "python3" is. If the launcher fails
  with "python: not found", change this line in launcher.py:
      os.system("python malware_sim.py")
  to:
      os.system("python3 malware_sim.py")
  Then run:
      python3 launcher.py
- Keep both Python files in the same working directory because the launcher
  refers to malware_sim.py by its filename.
- This is a benign demonstration: it creates test.txt, renames it to
  test.locked, and restores it. It does not encrypt files.
- Perform it only in the isolated lab VM. Revert the VM snapshot after the lab
  if required by your instructor.

Optional process monitoring:
   ps aux
   top
For file/process monitoring, use the instructor-approved monitoring tool.
For packet observation, open Wireshark on the isolated lab interface.

LAB 5 - INTRUSION DETECTION SYSTEM (IDS) CONFIGURATION
         AND ALERT ANALYSIS
============================================================

Purpose:
Install/run Suricata in monitoring mode and inspect IDS logs.

1. Install Suricata:
   sudo apt update
   sudo apt install suricata -y

2. Check installation/build:
   suricata --build-info

3. Identify the lab network interface:
   ip addr

4. Start Suricata on the correct lab interface (example: eth0):
   sudo suricata -i eth0

Keep it running while you generate harmless traffic from another authorized VM.
Use Ctrl+C to stop it when finished.

5. List Suricata logs:
   sudo ls -l /var/log/suricata/

6. View alert log if it exists:
   sudo tail -f /var/log/suricata/fast.log

7. View JSON event log if it exists:
   sudo tail -f /var/log/suricata/eve.json

8. Generate harmless authorized traffic from the lab client:
   ping -c 4 <LAB-TARGET-IP>

Notes:
- Replace eth0 with the interface connected to the isolated lab network.
- Alerts depend on the installed ruleset. Normal traffic may produce no alert.
- If no alert appears, record that accurately; do not invent an alert.
- Use only authorized lab traffic.

LAB 6 - FIREWALL RULE CONFIGURATION AND EVALUATION
============================================================

Purpose:
Use UFW to allow required traffic and restrict unnecessary inbound access.

CAUTION:
If connected remotely over SSH, allow SSH BEFORE enabling UFW or you may lock
yourself out. Use a VM console/recovery path.

1. Check UFW status:
   sudo ufw status verbose

2. Allow SSH if it is required for your lab administration:
   sudo ufw allow 22/tcp

3. Allow HTTP only if required for the experiment:
   sudo ufw allow 80/tcp

4. Enable UFW:
   sudo ufw enable

5. Review numbered rules:
   sudo ufw status numbered

6. Test the allowed service from the authorized client VM.

7. Remove the temporary HTTP rule if you added it and it is no longer needed:
   sudo ufw delete allow 80/tcp

8. Check final status:
   sudo ufw status verbose

Optional: disable UFW only if the instructor explicitly asks you to restore the
original state:
   sudo ufw disable

Do not disable institutional firewalls. Record the final policy and test results.

LAB 7 - VPN CONFIGURATION AND VERIFICATION USING WIREGUARD
============================================================

Purpose:
Create a WireGuard tunnel between two authorized Linux VMs.

Example lab tunnel addresses:
Peer A: 10.10.0.1/24
Peer B: 10.10.0.2/24

Use the actual addresses and endpoint details assigned by the instructor.

Run on BOTH peers:

1. Install WireGuard:
   sudo apt update
   sudo apt install wireguard -y

2. Generate a private/public key pair:
   wg genkey | tee privatekey | wg pubkey > publickey

3. Protect the private key:
   chmod 600 privatekey

4. Display ONLY the public key for exchange:
   cat publickey

Never share or disclose privatekey.

5. Create the WireGuard configuration using the instructor-approved peer
   details. The configuration file is normally:
   /etc/wireguard/wg0.conf

6. Bring the tunnel up after the configuration is completed:
   sudo wg-quick up wg0

7. Check interface and peer status:
   sudo wg

8. Test the other peer's VPN address.
   From Peer A:
   ping -c 4 10.10.0.2

   From Peer B:
   ping -c 4 10.10.0.1

9. Bring the interface down after the practical if instructed:
   sudo wg-quick down wg0

IMPORTANT:
The manual gives the key-generation and interface commands but does not provide
a complete peer-specific wg0.conf. Do not invent endpoint/public-key values.
Use the configuration details supplied by your instructor. Keep private keys
secret and do not expose configs containing private keys.

LAB 8 - SOCIAL ENGINEERING AWARENESS SIMULATION
============================================================

Purpose:
Run an approved awareness exercise and measure recognition/reporting without
collecting credentials or personal data.

The lab manual specifies NO separate command/code block for Lab 8.
Follow this safe procedure:

1. Obtain faculty/institutional approval.
2. Define the participant group and success criteria.
3. Prepare a simulated phishing-style message with clear training indicators.
4. Link only to a harmless training page or simulated form.
5. The form may record only a non-sensitive outcome, such as:
      Recognized
      Reported
      Ignored
6. Do NOT request or store:
      Passwords
      OTPs
      Financial information
      Personal or confidential information
7. Record results only in aggregate.
8. Explain the warning signs after the exercise.
9. Demonstrate the approved method for reporting suspicious messages.
10. Document recommendations.

Example of safe aggregate result format (fill with your actual observations):
   Total participants: <NUMBER>
   Recognized: <NUMBER>
   Reported: <NUMBER>
   Ignored: <NUMBER>

Common warning signs to explain:
- Urgent or threatening language
- Suspicious sender address
- Unexpected attachments
- Links with unusual or misspelled domains
- Requests for passwords, OTPs or financial details

There is no terminal command required by the lab manual.

LAB 10 - SECURITY ASSESSMENT OF AN INTENTIONALLY VULNERABLE
          WEB APPLICATION
============================================================

Purpose:
Assess a local intentionally vulnerable web app using OWASP ZAP, beginning with
passive analysis.

Tools:
OWASP Juice Shop (or instructor-approved vulnerable app), OWASP ZAP, browser,
isolated local lab.

1. Start the vulnerable web application using the method provided by your
   instructor. Use ONLY its local lab URL.
   Example URL format:
   http://127.0.0.1:<PORT>
   Do not assume a port; use the URL supplied by the instructor.

2. Start OWASP ZAP:
   zaproxy

   If the command is unavailable, open OWASP ZAP from the Applications menu.

3. Create/select the lab session in ZAP.

4. Configure the browser to use the ZAP local proxy as instructed by the lab
   setup. Use the proxy address/port shown in ZAP.

5. Open the instructor-provided local vulnerable application in the browser.

6. Browse the application normally while ZAP is open.

7. In ZAP, inspect:
   - Sites
   - History
   - Alerts

8. Begin with passive analysis. Do not run active scans unless the instructor
   explicitly authorizes them for the isolated lab target.

9. Record each relevant finding:
   - URL/endpoint
   - Evidence/alert
   - Risk/severity
   - Affected component
   - Possible impact
   - Recommended mitigation

10. Save/export the ZAP session/report only as instructed and keep it within
    the lab.

Important:
- Test ONLY the local/instructor-approved application.
- Do not direct ZAP at public websites.
- Do not use real credentials or data.
- Avoid destructive testing.
- A scanner alert alone is not proof that a vulnerability is exploitable.
