APPLIED CYBERSECURITY FUNDAMENTALS (CYS3001P) PRACTICAL WORKFLOW / WHAT
TO DO IN EACH LAB Selected experiments: 1, 2, 3, 4, 5, 6, 7, 8 and 10
Based on the DYPIU Applied Cybersecurity Fundamentals Lab Manual.

IMPORTANT LAB SAFETY - Perform scans, captures and assessments only on
explicitly authorized lab systems. - Use a Host-only/Internal virtual
network for vulnerable targets and security-testing exercises. - Never
scan or test public, institutional or third-party systems without
explicit authorization. - Do not collect real passwords, OTPs, financial
information or confidential personal data. - Use only
instructor-provided safe samples or simulations for malware analysis. -
Do not perform destructive exploitation, denial-of-service, persistence
or credential-theft activities. - Protect private keys, packet captures,
logs, evidence images and reports. - Report unexpected system or network
impact to the faculty immediately.

============================================================ LAB 1 —
NETWORK SCANNING AND RECONNAISSANCE USING NMAP Manual pages: 11–13

Aim: Identify active hosts, open ports, services and potential security
exposures using Nmap in an authorized lab.

Tools: - Kali Linux/Ubuntu VM - Nmap - Instructor-authorized target VM -
Host-only/Internal virtual network

What to do: 1. Start the testing VM and the instructor-assigned target
VM. 2. Confirm both VMs are connected to the same Host-only/Internal lab
network. 3. On the testing VM, open Terminal. 4. Display the testing
VM’s IP address and identify the lab interface: ip addr 5. Test
connectivity to the assigned target: ping -c 4 6. Discover active hosts
in the assigned lab subnet: nmap -sn Example from the manual: nmap -sn
192.168.56.0/24 7. Perform a basic scan of the assigned target: nmap 8.
Identify service versions: nmap -sV 9. Optional OS detection, only
against the assigned lab target: sudo nmap -O 10. Record reachable
hosts, open/closed/filtered ports, service names and versions. 11.
Discuss which unnecessary services should be disabled or patched.

What to write/record: - Testing VM IP and interface - Target VM IP -
Host discovery result - Open ports and their states - Detected services
and versions - Recommended services to disable or patch

Expected interpretation: - -sn performs host discovery without a normal
port scan. - A basic scan lists ports as open, closed or filtered. - -sV
attempts service/version detection. - Scanner output alone is not proof
that a vulnerability exists.

============================================================ LAB 2 —
NETWORK PACKET CAPTURE AND ANALYSIS USING WIRESHARK Manual pages: 14–16

Aim: Capture and analyze network packets and examine protocols, traffic
patterns and potentially suspicious activity.

Tools: - Wireshark - Linux/Windows VM - Authorized lab network -
Optional second lab VM

What to do: 1. Use an authorized lab interface such as eth0 or ens33. 2.
Open Wireshark. 3. Select the interface carrying the laboratory traffic.
4. Click Start to begin packet capture. 5. From the lab VM, generate
normal traffic using ping between authorized systems. 6. Generate DNS
traffic by resolving an approved domain or using the lab DNS service. 7.
Stop the capture. 8. Apply the following display filters one at a time:
icmp dns tcp udp ip.addr == 9. Select packets and inspect the protocol
details. 10. Examine Ethernet, IP, TCP/UDP and application-layer fields
where present. 11. Record the protocol, source, destination and
important observations. 12. Save the packet capture securely if required
by the instructor.

What to write/record: - Interface used - Traffic generated
(ping/DNS/other approved traffic) - Filters used - Source and
destination IP addresses - Protocol and relevant header fields -
Observations from selected packets

Expected interpretation: - ICMP packets show source/destination IPs and
ICMP type/code. - DNS traffic commonly uses UDP and contains
query/response information. - TCP packets contain source/destination
ports and TCP flags. - One packet alone is rarely sufficient to
establish malicious activity.

Safety: Capture only authorized lab traffic. Do not collect passwords or
confidential information.

============================================================ LAB 3 —
VULNERABILITY ASSESSMENT OF AN INTENTIONALLY VULNERABLE SYSTEM Manual
pages: 17–19

Aim: Identify and analyze vulnerabilities in an intentionally vulnerable
system in an isolated laboratory environment.

Tools: - Greenbone/OpenVAS or instructor-approved scanner -
Kali/Ubuntu - Intentionally vulnerable target VM - Isolated virtual
network

What to do: 1. Start the target VM and the vulnerability-scanner VM. 2.
Place both VMs on the same isolated virtual network. 3. Confirm the
target IP assigned by the instructor. 4. Check that the target is
reachable: ping -c 4 5. Optional service check before scanning: nmap -sV
6. Open the Greenbone/OpenVAS scanner console or web interface. 7.
Create a new scan target using only the instructor-assigned target IP.
8. Create a scan task. 9. Select the standard/safe assessment profile
recommended by the instructor. 10. Start the scan and wait for
completion. 11. Open the scan results. 12. Record the top findings and
their severity. 13. Note affected services/ports, CVE references (if
listed), severity scores and remediation guidance. 14. Convert the
findings into a concise recommendation table.

What to write/record: - Target IP and confirmation it is the assigned
lab VM - Scanner and scan profile used - Vulnerability/finding name -
Severity/risk rating - Affected port/service - CVE reference if
present - Recommended remediation

Expected interpretation: The report may contain CVE references, severity
scores, affected ports/services and remediation suggestions. Validate
findings; scanner results can include false positives.

Safety: Use only the assigned vulnerable VM. Do not scan
institutional/public systems or enable destructive exploitation modules.
Preserve the scanner report.

============================================================ LAB 4 —
SAFE MALWARE / SIMULATED MALICIOUS PROGRAM ANALYSIS Manual pages: 20–21

Aim: Analyze the behavior and characteristics of a safe sample or
simulated malicious program using a controlled sandbox.

Tools: - Isolated Windows/Linux VM - Instructor-provided safe
sample/simulation - Process Monitor/Process Explorer or equivalent -
Wireshark - SHA-256 utility

What to do: 1. Use an isolated VM with a clean snapshot and no access to
sensitive host resources. 2. Prefer Host-only networking. 3. Take a
snapshot named Clean-Analysis-State before analysis. 4. Copy only the
instructor-provided safe sample/simulation into the isolated VM. 5.
Calculate its SHA-256 hash before execution: sha256sum 6. Optionally
identify the file type: file 7. Start process/file monitoring tools such
as Process Monitor/Process Explorer or an equivalent. 8. Start Wireshark
if network behavior is part of the approved simulation. 9. Execute the
safe sample only inside the sandbox. 10. Observe process creation, file
changes and simulated network activity. 11. Record observations and
timestamps. 12. Stop the sample. 13. Revert the VM to the clean snapshot
after the practical.

What to write/record: - Sample filename and file type - SHA-256 hash -
Time of execution - Processes observed - Files created/changed -
Controlled network activity, if any - Tools used and observations

Expected interpretation: - The hash provides an identifier for the
sample. - A simulated program may create files/processes or generate
controlled traffic. - Static analysis examines a file without executing
it. - Dynamic analysis observes behavior while it runs.

Safety: Never execute unknown malware on a personal/production computer.
Do not connect the sandbox to an unrestricted network or upload
institutional samples to public scanning sites. Revert the snapshot
after the exercise.

============================================================ LAB 5 —
INTRUSION DETECTION SYSTEM (IDS) CONFIGURATION AND ALERT ANALYSIS Manual
pages: 22–25

Aim: Set up an IDS to monitor network traffic, generate alerts and
analyze detected events.

Tools: - Suricata or Snort - Linux VM - Authorized lab network - Second
lab VM for normal test traffic

What to do: 1. Use an isolated lab interface. The manual’s example
assumes eth0; replace it with the actual interface. 2. Update package
information: sudo apt update 3. Install Suricata: sudo apt install
suricata 4. Check the installed build information: suricata –build-info
5. Identify the lab network interface: ip addr 6. Check the Suricata
configuration for syntax errors if supported by the installed version.
7. Start Suricata in monitoring mode on the lab interface: sudo suricata
-i 8. From another authorized lab VM, generate normal traffic. 9.
Inspect the Suricata log/alert directory: sudo ls -l /var/log/suricata/
10. Review available alerts and interpret them. 11. Record alert
timestamps, source/destination, protocol and message/signature.

What to write/record: - Suricata version/build information - Interface
monitored - Test traffic generated - Alert details, if any -
Interpretation of each alert - If no alert appears, record that
honestly; do not invent one

Expected interpretation: - Normal ping or service traffic may or may not
trigger alerts depending on the installed ruleset. - Alert records
commonly include timestamp, source/destination, protocol and
message/signature. - A false positive is legitimate activity incorrectly
flagged as suspicious.

Safety: Use only lab traffic. Do not generate malicious payloads against
external systems. Protect log files and report unexpected alerts to the
instructor.

============================================================ LAB 6 —
FIREWALL RULE CONFIGURATION AND EVALUATION Manual pages: 26–28

Aim: Configure firewall rules controlling inbound and outbound traffic
and evaluate their effectiveness.

Tools: - Ubuntu/Kali Linux - UFW - Authorized test VM -
Host-only/Internal network

What to do: 1. Use a lab server and a second lab client on the
authorized lab network. 2. Check the current firewall status: sudo ufw
status verbose 3. If the instructor requires it, allow SSH before
enabling a restrictive policy when SSH is your administrative method:
sudo ufw allow 22/tcp 4. Enable UFW only when required for the exercise:
sudo ufw enable 5. Allow any other service explicitly required by the
experiment. Example HTTP rule: sudo ufw allow 80/tcp 6. Review the
numbered rules: sudo ufw status numbered 7. From the authorized client
VM, test an allowed service. 8. Test a service that should be blocked
according to the policy. 9. Remove the temporary HTTP rule if required:
sudo ufw delete allow 80/tcp 10. Record the final firewall policy and
test results.

What to write/record: - Initial firewall status - Rules added -
Services/ports allowed - Service tested from client - Whether
allowed/blocked tests behaved as expected - Final firewall status/policy

Expected interpretation: - An allowed service should be reachable from
the authorized client. - A service without an allow rule should be
blocked according to the active policy. - A firewall filters traffic
according to defined rules.

Safety: Use only the lab network. Do not disable institutional
firewalls. Keep a recovery/console path available. Verify SSH access
before applying a restrictive policy to a remote lab system. Document
all changes.

============================================================ LAB 7 —
VIRTUAL PRIVATE NETWORK (VPN) CONFIGURATION AND VERIFICATION Manual
pages: 29–30 and viva page 34

Aim: Establish and verify secure communication between authorized
systems using a VPN.

Tools: - Two Linux VMs - WireGuard - Host-only/Internal network

Example topology from the manual: - Peer A: 10.10.0.1/24 - Peer B:
10.10.0.2/24 Use the actual interface and addresses assigned by the
instructor.

What to do: 1. Start both authorized Linux VMs and connect them to the
Host-only/Internal lab network. 2. Install WireGuard on both VMs: sudo
apt update sudo apt install wireguard 3. Generate a private/public key
pair on each VM: wg genkey | tee privatekey | wg pubkey > publickey 4.
Protect each private key: chmod 600 privatekey 5. Create a WireGuard
interface configuration on each peer using the instructor-approved
topology. 6. Assign the VPN address to each peer. In the manual’s
example, Peer A uses 10.10.0.1/24 and Peer B uses 10.10.0.2/24. 7.
Exchange public keys only. Keep private keys secret. 8. Bring the
WireGuard interface up after the configurations are complete: sudo
wg-quick up wg0 9. Check interface and peer status: sudo wg 10. From
Peer A, test the VPN address of Peer B: ping -c 4 10.10.0.2 11. Record
the handshake status and connectivity result. 12. Bring the interface
down after the practical if instructed: sudo wg-quick down wg0

What to write/record: - Peer A and Peer B VPN addresses - Confirmation
that public keys were exchanged - Do not include private key values in
the report - WireGuard interface/peer status - Latest handshake and
transfer counters, if shown - Ping result through the VPN

Expected interpretation: - After traffic passes, sudo wg should show a
recent handshake/transfer counters. - A successful ping to the remote
VPN address demonstrates IP connectivity through the tunnel.

Safety: Never share private keys. Do not expose VPN configuration
containing secrets. Use only authorized lab peers and the
instructor-provided topology.

============================================================ LAB 8 —
SOCIAL ENGINEERING AWARENESS SIMULATION Manual pages: 35–37

Aim: Conduct an authorized social-engineering awareness simulation and
analyze common human-factor vulnerabilities and defensive measures.

Tools: - Instructor-approved awareness scenario - Test accounts or
simulated form - No real credentials, OTPs or sensitive data

What to do: 1. Obtain faculty/institutional approval for the simulation.
2. Define the participant group and success criteria. 3. Prepare a
simulated phishing-style message containing training indicators. 4.
Provide a harmless simulated link or training page. 5. Ensure the
form/page does not request or store passwords, OTPs, financial data or
personal information. 6. Record only aggregate outcomes such as: -
Recognized - Reported - Ignored 7. Explain the warning signs after the
exercise. 8. Demonstrate how a user should report a suspicious message
through the approved reporting channel. 9. Document recommendations to
improve awareness.

What to write/record: - Approval and scenario summary - Training
indicators included in the simulated message - Aggregate number of
recognized/reported/ignored outcomes - Warning signs explained -
Recommended defensive practices

Expected interpretation: Participants who recognize the training
indicators and report the message demonstrate effective awareness. Use
aggregate results to identify which defensive practices need
reinforcement.

Important: The manual does not specify a separate command/code block for
this experiment. Follow the approved procedure above. Do not build a
credential-harvesting page or collect real user information.

============================================================ LAB 10 —
SECURITY ASSESSMENT OF AN INTENTIONALLY VULNERABLE WEB APPLICATION
Manual pages: 40–41

Aim: Conduct a security assessment of an intentionally vulnerable web
application and document identified vulnerabilities and recommended
mitigation measures.

Tools: - OWASP Juice Shop or instructor-approved vulnerable web
application - OWASP ZAP - Web browser - Isolated local lab

What to do: 1. Run the vulnerable web application locally in the
isolated lab. 2. Open the application in a web browser using the
instructor-provided local URL. 3. Open OWASP ZAP and create/select the
lab session. 4. Configure the browser to use the ZAP proxy as
instructed. 5. Browse the application normally. 6. Observe the HTTP
requests and responses in ZAP. 7. Begin with passive analysis. 8. Review
the Sites, History and Alerts sections in ZAP. 9. Identify an
instructor-approved vulnerability category. 10. Record the URL/endpoint,
evidence, affected component, impact/risk and mitigation. 11. Prepare a
finding table.

Suggested finding table columns: - Finding / alert - URL or endpoint -
Evidence observed - Affected component - Risk/impact - Recommended
mitigation

Expected interpretation: A passive alert may identify missing headers,
insecure configuration or other issues depending on the application. Do
not claim a vulnerability is exploitable solely because a scanner lists
an alert; verify it within the safe lab context.

Safety: Test only the local/instructor-approved application. Do not use
real credentials or data. Avoid destructive testing. Keep the ZAP
session and reports within the lab.
